# Gemini Offload Setup and Model Support Update - Frozen Implementation Plan

> Status: frozen after initial creation. Do not edit this file during implementation.
> Base commit: `302ec94295ae6c5d175526a10c5b5b0e47e6a2fc` (`Harden durable Gemini offload runs`).
> Branch: `feat/setup-model-registry`.
> Progress, deviations, discoveries, and validation evidence belong only in
> `SETUP_MODEL_IMPLEMENTATION_LOG.md`.

## Objective

Improve first-run credential onboarding and make supported Gemini models easier
to update without turning gemini-offload into a fully user-configurable Gemini
API proxy or bloating the MCP tool surface.

The update should preserve gemini-offload's product identity: a curated,
filesystem-aware Vertex AI offload service with strong defaults for OCR,
multimodal processing, structured extraction, and durable background work.

## Confirmed product direction

1. Add one compact, read-only setup diagnostic tool for Vertex credentials and
   important local paths.
2. Keep the diagnostic tool schema empty and its description short so it adds
   negligible recurring context cost after onboarding is complete.
3. Allow a separate filesystem-capable agent tool to act on diagnostic guidance,
   but create no code, package, schema, or documentation dependency on any
   specific companion tool.
4. Record registered-artifact retrieval as a long-term roadmap item; do not build
   an artifact reader in this update.
5. Replace the thin model allowlist with a curated capability registry that makes
   maintainer-driven model additions small and reviewable; arbitrary user-provided
   model IDs are not a goal.
6. Keep generation controls intentionally narrow. Do not expose temperature,
   top-p, top-k, seed, safety thresholds, or similar expert tuning parameters.
7. Apply the product safety-filter policy internally rather than adding a public
   setting. The intended configurable-filter policy is explicit `OFF`, subject
   to current Vertex SDK/API verification.
8. Keep the current `call_gemini` plus `manage_gemini_run` topology. Tool splitting
   is not part of this update.
9. Preserve the core zero-configuration run-root fallback for compatibility, but
   make the local installer recommend and configure a persistent run directory.
10. Do not add monetary budgets, token budgets, or run deadlines in this update.

## Non-negotiable invariants

1. Setup diagnostics are read-only and never expose private keys, OAuth tokens,
   complete credential payloads, or other reusable secrets.
2. Missing or invalid setup returns a compact structured diagnostic instead of
   requiring a billable Gemini inference to discover the problem.
3. Existing valid manifests and environment-variable resolution order continue
   to work.
4. Credential rotation, quota-slot behavior, durable background execution, and
   the public `call_gemini`/`manage_gemini_run` contracts remain compatible.
5. Unsupported or unverified model-feature combinations fail closed before a
   long-running background job is started whenever practical.
6. Model capabilities and product defaults remain separate concepts.
7. Root and bundled workflow skill trees remain byte-for-byte synchronized.
8. No filesystem companion product is imported, invoked, or required by this
   package.

## Phase 1 - Compact setup diagnostic

### 1.1 Tool contract

Add one MCP tool named `check_gemini_setup` unless implementation evidence shows
that a different short name is materially clearer.

- Input schema: empty object with `additionalProperties: false`.
- Description: one short sentence, approximately ten words.
- The tool is diagnostic and read-only; no credential copying, manifest writing,
  config editing, directory relocation, or process restart.
- Normal setup failures return structuredContent with `ready: false`; they should
  not become opaque internal MCP errors.
- Output remains compact and omits raw credential material.

### 1.2 Diagnostic scope

The diagnostic should report only information useful for setup recovery:
- manifest resolution source and resolved manifest path;
- whether the manifest exists and parses;
- current Vertex location;
- credential count and compact per-entry project/status information;
- current output and run roots, including whether the run root uses temp storage;
- one concise next action when setup is incomplete.

### 1.3 Credential validation depth

Use layered status rather than overstating what was verified:

1. Resolve the selected manifest according to the existing precedence rules.
2. Parse the manifest and every referenced service-account JSON.
3. Construct scoped Google credentials without returning their contents.
4. Attempt a bounded OAuth token refresh when practical; this performs no
   Gemini inference and verifies that the credential can authenticate.
5. Distinguish `verified`, `invalid`, and `unverified` states when network access
   prevents a definitive result.

A successful token refresh does not claim that every Gemini model is enabled,
that Vertex AI is enabled for the project, or that quota is available. The
output and documentation must state this accurately.

### 1.4 Privacy and compactness

- Never emit private key fields, access tokens, refresh responses, or complete
  service-account JSON.
- Prefer configured display names and project IDs; mask or omit full client
  emails unless uniquely necessary for troubleshooting.
- Keep per-credential errors short and sanitized.
- Add a schema-size or description regression so future edits do not turn this
  one-time diagnostic into a large always-visible tool definition.
- Avoid initializing or mutating the process-global credential rotator merely to
  inspect setup; diagnostics should not alter cooldown or round-robin state.

## Phase 2 - Credential naming and setup internals

- Introduce precise internal names such as `get_vertex_credential_count` and
  setup-inspection helpers.
- Retain existing `get_key_count`, `ApiKeyLease`, and similar names only as
  compatibility aliases where removal would create unnecessary churn.
- Keep manifest precedence unchanged:
  `GEMINI_OFFLOAD_VERTEX_CREDENTIALS`, then `VERTEX_AI_CREDENTIALS`, then the
  default user-secret manifest path.

## Phase 3 - Internal safety policy

- Verify the current Google Gen AI SDK and Vertex AI support for explicit safety
  thresholds on every supported or newly added model.
- Define one internal safety configuration using `OFF` for configurable harm
  categories supported by the API.
- Do not expose a public safety parameter or advertise that non-configurable
  platform protections are disabled.
- Apply the setting through a single API-config construction path.
- Add tests proving the expected safety settings are sent and no MCP schema
  growth occurs.

## Phase 4 - Curated model capability registry

### 4.1 Registry boundary

Move model support metadata out of ad-hoc allowlist logic into a dedicated,
small registry module. A model addition should primarily require one registry
entry, supporting evidence, and contract tests—not scattered conditionals.

The registry should contain only capabilities relevant to gemini-offload:
- canonical model ID, release stage, and concise selection guidance;
- supported input and output modalities;
- thinking levels and thought-summary support;
- Google Search grounding support;
- JSON schema/structured-output support;
- image/PDF/video media-resolution support and allowed levels;
- image-output support when applicable;
- verified Vertex locations or location constraints when material;
- explicit safety-`OFF` compatibility status.

Capability status should allow `supported`, `unsupported`, and `unverified` so
unknown combinations fail closed rather than being guessed.

### 4.2 Capability versus product policy

Keep separate representations for:

- model capability: what the model/API accepts;
- product policy: what gemini-offload chooses by default for OCR and other work.

Do not silently replace the current image/PDF/video resolution defaults solely
because general Google guidance differs. Compare official documentation and a
small representative OCR probe before changing product defaults. Any default
change must be separately logged with quality/cost rationale.

### 4.3 Validation behavior

- Validate model existence through the registry.
- Validate only feature combinations the public request actually exposes.
- Return concise preflight errors naming the unsupported capability and supported
  alternatives.
- Preserve request compatibility where a capability remains supported.
- Do not add temperature, top-p, top-k, seed, max-token, or user-controlled
  safety fields.
- Treat the current `include_thinking` behavior accurately: determine whether it
  requests thought summaries rather than enabling reasoning, then preserve or
  migrate naming with an explicit compatibility plan.

### 4.4 `list_gemini_models`

Extend the existing tool rather than adding another discovery tool.

- Keep its no-argument input schema.
- Continue returning model IDs and concise selection guidance.
- Add a compact, machine-readable capability object per model.
- Avoid copying long model-card prose into the tool result or schema.
- Document which fields are verified versus unverified.

## Phase 5 - Current model refresh and research

- Use current official Gemini API and Vertex AI sources as primary evidence.
- Identify current stable/preview candidates relevant to OCR, multimodal analysis,
  throughput, and fallback use.
- Verify each candidate on Vertex AI, not merely the AI Studio/Gemini API surface:
  model ID, service-account authentication, location, input modalities, thinking,
  Search grounding, JSON schema, media resolution, and safety policy.
- Prefer metadata/list APIs and documentation before any inference.
- When live contract probes are necessary, keep them tiny, bounded, non-benchmark,
  and explicitly recorded in the log; stop probing a feature after a decisive
  failure.
- Add only models with enough verified capability information to support the
  public contract safely.
- Remove or deprecate stale entries only with replacement guidance and regression
  coverage.
- Consider a development-only registry-audit script that detects newly listed or
  disappeared models, but never treat runtime discovery as automatic authorization.

## Phase 6 - Installer, documentation, skill, and roadmap

### 6.1 Installer and paths

- Add an installer `RunDir` option with a persistent Windows default under the
  current user's local application-data directory.
- Emit `GEMINI_OFFLOAD_RUN_DIR` in the generated MCP config block.
- Preserve the server's existing temp-based fallback for users who do not run the
  installer or explicitly configure a path.
- Let `check_gemini_setup` warn concisely when the active run root is temporary.

### 6.2 Documentation

Update README and architecture documentation to cover:
- the compact setup-check workflow and manifest precedence;
- what local validation and token refresh do and do not prove;
- the capability registry and curated model-update policy;
- internal safety-filter policy without implying removal of non-configurable
  platform protections;
- use with a generic filesystem-capable companion when outputs live remotely;
- long-term registered-artifact retrieval as a roadmap item;
- explicit statement that no companion MCP is a dependency.

### 6.3 Workflow skill and plugin mirror

- Tell agents to call `check_gemini_setup` only for first-run, authentication, or
  path troubleshooting—not before every Gemini call.
- Teach the agent to use returned paths and concise `next_action` guidance with
  whatever filesystem capability is available.
- Keep setup instructions short in the main skill; place detailed manifest and
  model-capability guidance in references.
- Mirror the complete root skill tree into the plugin and retain byte-parity tests.

## Explicitly out of scope

- Implementing `read_gemini_artifact`, `get_run_output`, or arbitrary file reads.
- Declaring Desktop Commander or any other filesystem MCP as a dependency.
- Allowing arbitrary model IDs, user-supplied registry files, or environment-only
  model overrides.
- Exposing temperature, sampling controls, seed, token limits, or safety settings.
- Splitting `call_gemini` into multiple tools.
- Monetary/token budgeting or a run-wide deadline.
- Replacing the durable run store or changing its schema without evidence that a
  model/setup feature truly requires it.
- Broad Ruff/mypy cleanup unrelated to touched functionality.

## Validation gates

Before completion:

1. Existing full test suite remains green.
2. Setup diagnostic covers missing manifest, malformed manifest, missing key file,
   invalid credential JSON, successful local parsing, verified refresh, and
   network-unverified behavior without leaking secrets.
3. Tool list exposes exactly one additional compact setup tool; schema and
   description size remain bounded.
4. Safety configuration is tested against current SDK object construction and,
   where necessary, a minimal live Vertex probe.
5. Model registry tests cover every supported model, capability-driven validation,
   concise discovery output, and stale/unknown model rejection.
6. Any newly supported model passes the documented Vertex contract probes.
7. MCP 1.x and 2.x stdio smoke tests pass without requiring a normal inference.
8. Installer output is valid and uses a persistent run root by default while the
   server fallback remains compatible.
9. Wheel build, compileall, `git diff --check`, secret/path scan, version parity,
   and root/plugin skill parity pass.
10. Final Git status contains only intentional changes and these two implementation
    records unless commit scope deliberately excludes them.

## Implementation order and checkpoint discipline

Use bounded checkpoints rather than keeping one phase open indefinitely:

1. Baseline and current-source audit.
2. Setup diagnostic internals and focused tests.
3. MCP tool exposure, installer, and setup documentation.
4. Safety-policy verification and implementation.
5. Model-registry extraction with no model-set change.
6. Official capability research and current-model refresh.
7. Capability-driven validation and discovery-output update.
8. Plugin/skill synchronization and full release audit.

After each checkpoint:
- run focused tests, then the full suite when the checkpoint changes behavior;
- append implementation evidence and unexpected findings to the log;
- keep source changes small enough to review independently;
- do not claim a capability verified by documentation or mocks alone when a
  bounded Vertex contract probe is required.
