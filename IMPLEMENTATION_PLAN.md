## Objective

Harden the run-oriented Gemini offload plugin for durable background execution while preserving the current MCP surface wherever practical. The work prioritizes correctness under path manipulation, process crashes, concurrent resume/control calls, partial writes, and context/process restarts. Structural cleanup follows only after behavior is protected by tests.

## Non-negotiable invariants

1. Caller-visible item IDs are metadata, not filesystem path components.
2. Every internally managed run path resolves beneath `GEMINI_OFFLOAD_RUN_DIR` (or its default root); symlink/path traversal must not escape it.
3. Internally managed output artifacts resolve beneath their run's `outputs/` directory and have collision-free storage names.
4. Explicit caller-provided absolute output paths remain supported by the existing public contract, but are never confused with managed run artifacts.
5. Durable state writes are atomic where replacement semantics apply; append-only records are never rewritten in place.
6. A `completed` item may be skipped during resume only when its recorded artifacts still exist and match recorded integrity metadata.
7. At most one active worker lease may own a run. Stale workers must be unable to overwrite state after ownership changes.
8. Worker startup and fatal worker errors must transition durable status instead of leaving a false `running` state.
9. Public MCP responses remain compact receipts plus authoritative `structuredContent`.
10. Root workflow skill and bundled plugin workflow skill remain byte-for-byte synchronized.

## Phase 1 - Filesystem and process safety hardening

### 1.1 Opaque item IDs and collision-free managed outputs

- Validate item IDs as non-empty strings with a reasonable size bound, but do not require path-safe characters.
- Enforce uniqueness of item IDs within a run.
- Introduce an internal storage key derived from item index (not caller ID) for managed output filenames.
- Persist whether an output is `managed` versus caller-specified.
- Ensure generated paths remain under `<run_dir>/outputs/` after resolution.

### 1.2 Run directory confinement

- Add strict run-id validation for server-generated/management IDs.
- Resolve management `run_dir` arguments and require an immediate child of the configured run root with a valid run ID.
- Reject `..`, alternate absolute directories, and symlink escapes.
- Validate persisted plan identity (`run_id`, `run_dir`, lifecycle) before resume/worker execution.

### 1.3 Atomic durable artifact writes

- Generalize atomic byte/text replacement using same-directory temporary files, flush, fsync, and `os.replace`.
- Use it for text/JSON outputs, manifests, image sidecars, plan/status/locator/control replacement files.
- Preserve append-only event behavior in Phase 1; Phase 2 moves event durability into the transactional store.

### 1.4 Artifact integrity and safe resume

- Record artifact metadata for completed background items: absolute path, byte count, SHA-256, and artifact role.
- Before skipping a completed item on resume, verify every recorded artifact exists, is a regular file, remains within the expected managed root when managed, and matches byte count/hash.
- If verification fails, reset that item to pending and re-execute it; record a recovery event/reason.
- Maintain backward compatibility for old status records by treating missing integrity metadata as not safely resumable.

### 1.5 Startup/failure transitions and duplicate-resume guard

- Keep newly spawned background runs in `starting` until the worker has acquired ownership and begins execution.
- Catch fatal worker bootstrap/execution failures and persist `failed` plus an explanatory worker error/event when the worker still owns the run.
- Add an atomic short-lived resume claim around liveness-check + spawn to close the current double-spawn race before the database lease exists.
- Ensure a superseded worker raises/observes ownership loss and stops mutating run state.

### 1.6 Phase 1 validation

Regression tests must cover at least:
- malicious/path-like item IDs cannot escape or alias managed outputs;
- duplicate item IDs are rejected;
- arbitrary/out-of-root `run_dir` and traversal run IDs are rejected;
- symlink escape is rejected where the platform permits the test;
- interrupted/partial output replacement leaves either old or new complete content;
- missing/tampered completed artifacts are re-run on resume;
- worker bootstrap failure persists terminal failure;
- concurrent resume attempts cannot both spawn workers.

## Phase 2 - Durable transactional run store

Introduce a standard-library SQLite run store under the configured run root.

### 2.1 Store design

- SQLite database in WAL mode with foreign keys enabled and explicit transactional boundaries.
- Tables for runs, items, artifacts, events, and worker leases.
- Schema versioning/migration table from day one.
- JSON payloads may store request/result details, but lifecycle/ownership/query-critical fields must be relational columns.

### 2.2 Transactional lease and fencing

- Worker acquisition/resume uses `BEGIN IMMEDIATE` (or equivalent) to atomically inspect liveness/state and increment a monotonic fencing generation.
- Each worker carries `(run_id, lease_generation, token)`.
- Every state-mutating transaction verifies the active generation/token before commit.
- Heartbeat/lease timestamps make crashed ownership reclaimable after a bounded stale interval.
- A stale worker can finish an external Gemini call, but cannot publish artifacts/status after losing its fence.

### 2.3 State machine

Define and enforce explicit run/item transitions rather than free-form status strings. At minimum:
- run: queued/starting/running/stopping/canceling/completed/failed/stopped/canceled;
- item: pending/running/completed/failed/stopped/canceled.
Illegal transitions fail closed and are covered by unit tests.

### 2.4 Events and snapshots

- Commit status mutation and corresponding event in the same database transaction.
- Keep filesystem `status.json`/`events.jsonl` only as compatibility/export views if retained; they must not be the source of truth.
- `manage_gemini_run list/status/progress` reads the durable store.

### 2.5 Recovery

- On server/worker startup, reconcile leases and stale `starting/running` runs.
- Resume selects only items whose terminal artifacts fail validation or whose state is non-terminal.
- Forced cancel cannot be undone by a stale worker because of fencing.

## Phase 3 - Architecture separation

After the durable behavior is green, split responsibilities without changing the MCP contract:

- `run_store.py`: SQLite schema, transactions, state machine, leases/fencing, event queries.
- `artifacts.py`: path confinement, atomic writes, hashes, artifact validation.
- `run_service.py`: normalization/materialization, orchestration, resume/recovery, control semantics.
- `worker.py` / `run_worker.py`: thin worker process lifecycle.
- `server.py`: MCP schemas, argument adaptation, compact result wrapping, transport only.
- Keep Gemini API/client/quota concerns in `gemini_client.py` and `keys.py`.

Use dependency injection or narrow interfaces so orchestration tests do not need real subprocesses, real Gemini calls, or real credentials.
